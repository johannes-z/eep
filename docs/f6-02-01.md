# F6-02-01 - Light and Blind Control, Application Style 1

## Quelle

EnOcean Equipment Profiles (EEP), Version 2.6.8, Dec 31, 2017, pages 15-16.

## Profilkennung

| Feld      | Wert                                          |
| --------- | --------------------------------------------- |
| RORG      | `F6`                                          |
| Telegramm | RPS Telegram                                  |
| FUNC      | `02`                                          |
| Funktion  | Rocker Switch, 2 Rocker                       |
| TYPE      | `01`                                          |
| Typ       | Light and Blind Control - Application Style 1 |

This EEP definition is based on the assumption that a RPS switch module, e.g. PTM200, is installed in a 0-STATE up position. Application Style 1 is widely used in EU but may be found in other markets as well.

For clarification reasons, the EEP specification shows a PTM200 transmitter module from EnOcean GmbH. PTM200 transmits RPS telegrams and is one possibility for applications that require an EEP F6-02-xx. PTM200 does not support transmission of teach-in telegrams.

The button naming used below refers to CHANNEL and STATE of the PTM200. Thus, `Button AI` means STATE `I` on CHANNEL `A`.

There are two different message types, the N-message and the U-message, which need to be identified from the Status Field of an EnOcean RPS telegram. For that reason not only the data bytes are given for each EEP, but the T21 and NU bits of the Status Field are listed as well.

| Offset | Size | Bitrange      | Data              | ShortCut | Description | Valid range                               |
| -----: | ---: | ------------- | ----------------- | -------- | ----------- | ----------------------------------------- |
|      0 |    3 | DB0.7...DB0.5 | Rocker 1st action | R1       | -           | See enum below                            |
|      3 |    1 | DB0.4         | Energy Bow        | EB       | -           | `0`: released; `1`: pressed               |
|      4 |    3 | DB0.3...DB0.1 | Rocker 2nd action | R2       | -           | See enum below                            |
|      7 |    1 | DB0.0         | 2nd Action        | SA       | -           | `0`: No 2nd action; `1`: 2nd action valid |

#### R1 and R2 enumeration

The same enumeration applies to Rocker 1st action (`R1`) and Rocker 2nd action (`R2`):

| Value | Button    | Application meaning                                   |
| ----: | --------- | ----------------------------------------------------- |
|   `0` | Button AI | Switch light on, dim light down, or move blind closed |
|   `1` | Button A0 | Switch light off, dim light up, or move blind open    |
|   `2` | Button BI | Switch light on, dim light down, or move blind closed |
|   `3` | Button B0 | Switch light off, dim light up, or move blind open    |

## Teach-in and Security

- Teach-in method: RPS teach-in.
- Direction: unidirectional.
- PTM200 does not support transmission of teach-in telegrams; the EEP and sender ID may therefore need to be supplied manually by the receiver/controller.
- Encryption supported: no.
- Security level format: -.

## Home Assistant

F6-02-01 exposes four read-only binary sensors under the same device: **AI**, **A0**,
**BI**, and **B0**. Each represents a momentary physical button, not a latched switch
or an outgoing command.

- All four default to Off. A press turns the identified button On; two identified
  simultaneous presses turn both corresponding sensors On.
- A release turns all four Off, including U-message releases without button identities.
- U-messages cannot identify individual buttons, so all four sensors show Off even
  when such a telegram indicates that three or four buttons are pressed. The raw
  MQTT payload still includes the aggregate press state and button count.
- Server startup clears saved button presses back to Off. An MQTT reconnect within
  the same server process preserves the current live state.
- Availability is independent of button state: an offline device still appears
  unavailable in Home Assistant.

All four sensors share the existing `eep/binary_sensor/<sourceId>/state` JSON topic
(or the configured base topic). Its aggregate `state`, `pressed`, `messageType`,
`buttons`, and `buttonCount` fields retain their existing meanings. Before the first
report, the payload is `{"state":"OFF"}`.

Discovery automatically removes the old single aggregate sensor and creates the
four button sensors; existing devices do not need to be paired again. Automations
using the old aggregate entity must be updated to use the appropriate button sensor.
